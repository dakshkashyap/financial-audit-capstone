● Good questions — let me clear both up.

  What Stage 0 does (the prof-friendly version)

  Stage 0 is a deterministic, no-LLM "pre-audit" gate that runs before any 
  language model. Its whole job is to catch the errors it can prove
  mathematically, and stay silent on everything else. It exists to kill the
  over-auditing problem (the 50% false alarms on clean statements).

  The key idea is that the transaction narrative is a ground-truth oracle. Each
  AuditBench table comes with a transaction story ([Explanation: $X = $a + $b],
  [contributing to row N]) that says what each line should be. So Stage 0
  doesn't need to "judge" anything — it just recomputes the arithmetic and 
  checks the accounting identities, then compares to what the table actually
  shows.

  It has two halves, splitting the four AuditBench error types by what kind of
  evidence catches them:

  Stage 0A — Arithmetic Verifier (SymPy + pandas) — owns the numeric errors:
  - Numerical Error (a value was changed) → recompute the row from the
  transaction oracle; if the stated value disagrees, flag it and emit the 
  correct number.
  - Missing Row (a row was deleted) → a transaction describes a row that isn't
  in the table, and a subtotal is short by exactly that row's value.

  Stage 0B — Equation Checker (pure Python) — owns the structural errors:
  - Redundant Row (an extra unsupported row) → a subtotal is over by exactly
  that row's value, and no transaction explains the row.
  - Misclassification (a real row in the wrong section) → a section is off by
  exactly the moved row's value while the grand total still balances.
  - It also checks definitional identities: Assets = Liabilities + Equity, the
  income-statement chain, cash-flow sums.

  The one design principle to emphasize to the prof: precision-first, abstain by
  default. Stage 0 only "fires" when a subtotal is off by exactly the
  implicated value (corroboration). If the evidence is ambiguous, it returns
  None (abstain) and hands the case to the LLM stage. That's why clean
  statements produce 0% false positives — clean books foot perfectly, so nothing
  is ever "off by exactly X," so the gate stays quiet. When it does fire it's
  right ~92–95% of the time and free.

  One-line framing: "Stage 0 turns the parts of auditing that are really 
  arithmetic back into arithmetic — done by Python, not guessed by an LLM."

  The honest verdict — is it a "massive improvement"?

  On the over-auditing problem the project targets: yes, massive. On clean
  statements Success Rate went 0.000 → 0.640, false alarms were halved (50% → 
  25.3%), and corrected-table BLEU went 0.45 → 0.98 (the baseline rewrites
  correct tables; IntelliAudit leaves them alone).

  On the 50/50 benchmark overall: it's a trade, not a uniform win. The same
  conservatism that kills false alarms costs error-detection recall on
  single_error (SR 0.50 → 0.29). But AuditBench's 50/50 error rate is
  unrealistic — real statements are mostly correct, where false alarms are the
  expensive failure. Weighting by clean share:

  │ 90:10 (realistic audit) │ 0.050       │ 0.605 (~12×)    │

  The strongest scientific finding (worth the paper)

  Prompt-grounding alone did NOT fix over-auditing. My first Stage 2 prompt
  (which listed the four error types up front) actually raised false alarms to
  61% — worse than baseline. What fixed it was giving the symbolic layer hard 
  authority (the deterministic veto + a conservative-by-default prompt). That's
  direct evidence for the neuro-symbolic thesis: you can't ask an LLM to stop 
  over-auditing — the deterministic checks have to be able to override it.

  Why single_error regressed (and how to fix it — not yet done)

  The veto flips an LLM "Incorrect" to "Correct" whenever the table is
  verified_consistent — sound on truly-clean tables, but ~13% of error tables
  also pass (their error leaves no arithmetic trace), so 15 real errors got
  wrongly cleared. Three tunable levers would recover most of it: (1)
  evidence-calibrated conservatism (conservative only when verified, audit
  normally otherwise — right now it's globally conservative), (2) tighter 
  verified_consistent, (3) a type-aware veto (only override Numerical/Missing
  claims, never Redundant/Misclassification).
